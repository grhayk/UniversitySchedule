================================================================================
              SCHEDULE GENERATION — HOW IT WORKS
================================================================================

The goal: take all GroupSubjectWithLecturer records and automatically produce
a conflict-free 2-week schedule (numerator + denominator) for the entire
university.

This is an NP-hard constraint satisfaction problem. We use Google OR-Tools
CP-SAT solver to find a solution.


================================================================================
1. THE BIG PICTURE (GenerateScheduleHandler)
================================================================================

The handler does 6 steps:

  Step 1 — Load data from DB
  Step 2 — Build a list of "demands" (what needs to be scheduled)
  Step 3 — Expand demands into individual "events" (lesson slots)
  Step 4 — Call the CP-SAT solver
  Step 5 — Map solver output back to Schedule entities
  Step 6 — Save everything to DB


================================================================================
2. STEP 1: LOAD DATA
================================================================================

We load:
  - All active GroupSubjectWithLecturer records (with Subject, SubjectConfigs,
    Group hierarchy, Flow and FlowGroups)
  - All SubjectClassroom records (which classrooms are valid for which subject)
  - All Classrooms with their Characteristics (seat capacity)
  - All TimeTables ordered by start time (to map slot index -> TimeTableId)
  - Student counts per group (to check classroom capacity)


================================================================================
3. STEP 2: BUILD DEMANDS
================================================================================

A "LessonDemand" represents one thing that needs to be scheduled. For example:
"Group CS-201 needs Calculus lectures by Prof. Smith, 2 hours per 2-week cycle"

For each GroupSubjectWithLecturer, we resolve:

  - LecturerId, SubjectId     — from LecturerSubject
  - Hours                     — from SubjectConfig (for that Subject + LessonType)
  - BusyGroupIds              — which groups become "busy" when this lesson runs
  - ValidClassroomIds          — which classrooms can host this (filtered by
                                 SubjectClassroom + seat capacity >= student count)
  - ScheduleGroupIds          — which groups to attach to the Schedule entity
  - SemesterId                — from the group

BusyGroupIds logic (prevents group conflicts):
  - Parent group lecture:  parent + ALL children are busy
  - Child group practical: child + parent are busy
  - Flow:                  all flow groups + all their children are busy

If any demand has 0 valid classrooms, we fail early with an error.


================================================================================
4. STEP 3: EXPAND TO EVENTS
================================================================================

Each demand with Hours = H creates H individual "LessonEvent" objects.
For example, a demand with Hours = 3 creates 3 events.

Each event is a single lesson slot that needs to be placed somewhere in the
2-week grid.


================================================================================
5. THE TIME GRID
================================================================================

  2 weeks × 5 days × 6 slots = 60 total timeslots

  Timeslot encoding:
    timeslot = weekIndex * 30 + dayIndex * 6 + slotIndex

    weekIndex: 0 = numerator week, 1 = denominator week
    dayIndex:  0 = Monday ... 4 = Friday
    slotIndex: 0 = 1st pair ... 5 = 6th pair

  Example: timeslot 37 = week 1, day 1, slot 1
           → denominator week, Tuesday, 2nd pair


================================================================================
6. STEP 4: THE CP-SAT SOLVER (ScheduleGenerator.cs)
================================================================================

This is the core algorithm. It takes the demands + events and finds a valid
assignment of (timeslot, classroom) to each event.

--- VARIABLES ---

For each event e:
  timeslotVars[e]  — which of the 60 timeslots (IntVar, range 0-59)
  classroomVars[e] — which classroom ID (restricted to valid ones)

For classrooms, we use an index trick:
  classroomIndexVars[e] — index into the demand's ValidClassroomIds list
  Then an AllowedAssignments table maps index -> actual classroom ID
  This avoids namespace conflicts and handles arbitrary classroom ID values.

--- HARD CONSTRAINTS (must be satisfied) ---

1. CLASSROOM NO-OVERLAP
   No two events can use the same classroom at the same time.
   We create: combined[e] = timeslot[e] * maxClassroomId + classroom[e]
   Then: AddAllDifferent(all combined values)
   This encodes the (timeslot, classroom) pair as a single integer.

2. LECTURER NO-OVERLAP
   Events with the same lecturer must have different timeslots.
   We group events by lecturer, then: AddAllDifferent(timeslots in group)

3. GROUP NO-OVERLAP
   Events that make the same group "busy" must have different timeslots.
   We group events by each BusyGroupId, then: AddAllDifferent(timeslots)
   This naturally handles parent-child and flow relationships.

4. HOURS DISTRIBUTION
   Events from the same demand must be split across the 2 weeks:
     - Even hours (H=2,4): exactly H/2 in each week
     - Odd hours (H=1,3): ceil(H/2) in one week, floor(H/2) in the other
   We use a BoolVar isInWeek0[e] (true if timeslot < 30) and constrain
   the sum of isInWeek0 values for each demand's events.

5. NO SAME-SUBJECT SAME-DAY
   Two events of the same demand cannot fall on the same day (across both
   weeks). We compute dayVars[e] = timeslot / slotsPerDay (gives 0-9 for
   10 total days) and: AddAllDifferent(dayVars for same demand)

--- SOFT CONSTRAINTS (objective to minimize) ---

AVOID LATE SLOTS
  Slot 4 (5th pair): penalty = 1
  Slot 5 (6th pair): penalty = 3
  The solver minimizes the total penalty, preferring earlier timeslots.

--- SOLVING ---

The solver runs for up to 60 seconds. It returns either:
  - Optimal:  best possible solution found
  - Feasible: a valid solution (may not be the best)
  - Infeasible / other: no valid schedule exists with current data


================================================================================
7. STEP 5: MAP OUTPUT TO SCHEDULE ENTITIES
================================================================================

For each placed event, we decode the timeslot back:
  weekIndex = timeslot / 30          → WeekType (Numerator/Denominator)
  dayIndex  = (timeslot % 30) / 6    → added to StartDate for ScheduleDate
  slotIndex = timeslot % 6           → mapped to TimeTableId (ordered list)

We create a Schedule entity with:
  SubjectId, LecturerId, LessonTypeId  — from the demand
  ClassroomId                          — from solver output
  TimeTableId                          — from slotIndex mapping
  WeekType                             — from weekIndex
  ScheduleDate                         — StartDate + weekIndex*7 + dayIndex
  SemesterId                           — from the demand
  ScheduleGroups                       — from demand's ScheduleGroupIds


================================================================================
8. STEP 6: SAVE
================================================================================

All Schedule entities are saved in a single SaveChangesAsync call for
atomicity.


================================================================================
9. API USAGE
================================================================================

  POST /api/schedules/generate
  Body: { "startDate": "2026-02-09" }

  startDate = first Monday of the semester

  Response: { totalSchedulesCreated, totalDemandsProcessed, solverStatus }


================================================================================
10. EXAMPLE FLOW
================================================================================

  Input data:
    - Group "CS-201" has SubjectConfig: Calculus, Lecture, Hours=2
    - Group "CS-201a" has SubjectConfig: Calculus, Practical, Hours=1
    - Group "CS-201b" has SubjectConfig: Calculus, Practical, Hours=1
    - Prof. Smith teaches Calculus lectures
    - Prof. Jones teaches Calculus practicals

  Demands built:
    D0: Calculus Lecture  for CS-201  (Hours=2, busy=[CS-201,CS-201a,CS-201b])
    D1: Calculus Practical for CS-201a (Hours=1, busy=[CS-201a,CS-201])
    D2: Calculus Practical for CS-201b (Hours=1, busy=[CS-201b,CS-201])

  Events expanded:
    E0 -> D0, E1 -> D0  (2 lecture events)
    E2 -> D1             (1 practical event)
    E3 -> D2             (1 practical event)

  Solver finds, for example:
    E0: timeslot=0  (Mon slot1 week1), classroom=101
    E1: timeslot=30 (Mon slot1 week2), classroom=101
    E2: timeslot=7  (Tue slot2 week1), classroom=205
    E3: timeslot=8  (Tue slot3 week1), classroom=205

  No conflicts:
    - Prof. Smith's lectures are on different timeslots (0, 30) ✓
    - CS-201 is busy at 0,30,7,8 — all different ✓
    - CS-201a is busy at 0,30,7 — all different ✓
    - CS-201b is busy at 0,30,8 — all different ✓
    - Classroom 101 used at timeslots 0 and 30 — different ✓
    - Classroom 205 used at timeslots 7 and 8 — different ✓
